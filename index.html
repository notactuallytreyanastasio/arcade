arcade 0.1.0 · MIT

A game engine for March games that run in the browser.

The core is pure: maths, a seedable RNG, a camera, a 2D drawing vocabulary, a synth, and the replay of a game's reducer. A thin JS-only shell runs the frame loop, canvas, pointer and audio. A game supplies the rules, the scene and the sounds; the engine never looks inside a game's model, messages or effects.

Pure core

Every fn in the core is cap pure with needs (). Hooks are plain fn parameters and extension points are type parameters, so a game's cue, event and model types pass through the engine unopened.

Thin shell

Arcade.Web.* and its arcade_*.mjs glue are the only JS-target code. The shell executes a list of canvas calls and decides nothing; every drawing decision is made in the core, where it is testable.

Reproducible

The same seed and the same actions give the same state bit for bit, natively and on JS, unless the computation goes through libm, where V8 and the native libm can differ by an ulp or two. The limits are listed below.

Three packages

Versioned together at 0.1.0 and published separately. The engine names no game; dependencies point one way.

arcade

lib

The pure core and, under lib/arcade/web/, the JS shell.

  • Arcade.Rng SplitMix64 as a value: every draw returns (value, Rng)
  • Arcade.Camera perspective or orthographic; world to screen, rays
  • Arcade.Draw, Arcade.Canvas, Arcade.Svg draw ops as data, compiled to canvas calls or SVG
  • Arcade.Synth, Arcade.SynthFeed a polyphonic synth as a value, fed by a game's own cue type
  • Arcade.Replay a game's reducer folded over its actions
  • Arcade.Vec2, Vec3, Num, Numerics, U64, Float32, Html
  • Arcade.Web.Runtime, Input, Paint, Audio, SynthHost, SynthWorklet and the rest of the shell

arcade_physics

lib · depends on arcade

Fixed-step simulation, kinematics, the libm replay seam and gesture measurement. Pure.

  • Arcade.Physics.Sim a clock, timed events, sampled paths and the step loop run_steps
  • Arcade.Physics.Kinematics ballistic motion, friction, reflection, bounds
  • Arcade.Physics.Trig recorded sines in place of libm, for bit-exact replays across targets
  • Arcade.Physics.Gesture a flick measured from pointer samples

arcade_testkit

lib · depends on arcade · a dev-dep

The suite harness, golden-row readers and digests. It holds IO and panics, so it goes on test paths only.

  • Arcade.Test.Harness cases and outcomes; a suite passes only when it prints HARNESS PASS with non-zero counts
  • Arcade.Test.GoldenIo golden rows as tokens; floats compared on every bit, or within a declared ulp tolerance for libm on JS
  • Arcade.Test.Digest a 32-bit digest of a run, so two targets can be compared by one number

The dependency lines

The packages are not in the forge registry yet. Once 0.1.0 is published, a game's forge.toml names them by version:

[deps]
arcade = "0.1.0"
arcade_physics = "0.1.0"      # only if it uses Arcade.Physics

[dev-deps]
arcade_testkit = "0.1.0"

Until then, and for a game that lives in the engine's source tree as the example does, by path:

[deps]
arcade = { path = "../.." }
arcade_physics = { path = "../../physics" }

[dev-deps]
arcade_testkit = { path = "../../testkit" }

How a game plugs in

The game's side, as examples/putt does it.

  1. Rules are a pure reducer, play(rules, action, state) : Result(state, why). Every random choice is drawn from an Arcade.Rng carried in the state, so Arcade.Replay.replay rebuilds any game from its seed and its actions.
  2. Simulation steps with Arcade.Physics.Sim.run_steps and the helpers in Kinematics.
  3. The view builds a Rig (Perspective for a 3D scene, Orthographic for a top-down one), projects with Arcade.Camera, and returns a List(DrawOp).
  4. Sound is the game's own cue type and a voices(SynthConsts, cue) fn. The game emits AudioCmd(cue) values; the engine's feed and worklet render them.
  5. The shell is one WebHooks record handed to Arcade.Web.Runtime.launch: boot, update, perform, the tick, resize, pointer and visibility msgs, the scene, an overlay and the data-* marks.

The whole of step 5 in the demo

This is the end of examples/putt/shell/putt_shell.march, copied into this page when the site was built. "green" is the id of the page's canvas; everything the hooks call is the game's own code.

fn hooks() : Arcade.Web.Runtime.WebHooks(Held, PuttMsg, PuttFx) do
  {
    hook_num: Arcade.Numerics.make(),
    hook_boot: fn (w, h, seed) -> boot(w, h, seed),
    hook_update: fn (b, x) -> held(update(unheld(b), x)),
    hook_perform: fn (_dispatch, effects) -> perform(effects),
    hook_tick: fn t -> PmTick(t),
    hook_resize: fn (w, h) -> PmResize(w, h),
    hook_down: fn raw -> Some(PmDown(track(raw))),
    hook_move: fn raw -> Some(PmMove(track(raw))),
    hook_up: fn raw -> Some(PmUp(track(raw))),
    hook_cancel: Some(PmCancel),
    hook_listen: fn (_model, _dispatch) -> (),
    hook_visible: fn shown -> PmVisible(shown),
    hook_scene: fn b -> scene(unheld(b)),
    hook_overlay: fn _ -> [],
    hook_settle: fn _ -> (),
    hook_marks: fn b -> marks(unheld(b))
  }
end

fn main(_f : Cap(IO.Foreign)) : () do
  match Arcade.Web.Runtime.launch("green", fn () -> hooks()) do
  Ok(_) -> ()
  Err(why) -> panic(why)
  end
end

Building it

The game's Makefile includes arcade.mk, which defines the module paths and the JS flags. forge build puts only lib/ and the deps on the module path, so a shell in shell/ is built with march directly:

ARCADE := ../..
include $(ARCADE)/arcade.mk
WEB_LIB := lib:$(ARCADE_LIB):$(ARCADE_PHYSICS_LIB):shell
web:
	MARCH_LIB_PATH=$(WEB_LIB) march $(ARCADE_JS_FLAGS) -o dist/game.mjs shell/game_shell.march

arcade.mk, scripts/ and examples/ belong to the source tree and are not published with the packages.

The demo is that build

Putt is a static site: putt.mjs built from the shell above, the audio worklet's own build, March's runtime modules and the engine's glue. Every random choice in it is drawn from an Arcade.Rng seeded at launch, so a game is its seed plus the actions it accepted, and Arcade.Replay.replay rebuilds it.

Where bit-exact stops

  • libm on JS. sin, cos, log and atan2 differ from native on a few percent of arguments by 1 ulp (next_gaussian, which chains them, by up to 2). Physics that must replay across targets goes through Arcade.Physics.Trig.
  • Float32. sinf, expf and powf are double libm rounded to Float, not a Float libm, so they can differ from a platform's sinf by one Float ulp.
  • Float literals on JS print with 12 significant digits, so a constant with more comes from Arcade.Numerics, built from text.
  • Int on JS is a double, exact to 253 − 1. Anything wider is Arcade.U64.
  • The shell is JS only. Arcade.Web.* builds for the JS target and draws on a canvas. The pure core also runs natively, which is how its suites are checked on both targets.
